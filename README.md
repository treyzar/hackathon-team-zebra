# Zebra — платформа онлайн-обучения

Курсы состоят из модулей, модуль — из упорядоченных шагов. Шаг — это теория
или задание: одиночный выбор, множественный выбор, свободный ответ
(с файлами) или программирование на Python с проверкой тестами.

- **Ученик** проходит опубликованные курсы и отправляет решения.
- **Куратор** проверяет решения учеников своей группы.
- **Администратор** пишет курсы, записывает на них учеников, управляет
  группами и ролями.

| Часть | Технологии |
|---|---|
| Бэкенд (`backend/`) | Python 3.12, FastAPI, SQLAlchemy (async), PostgreSQL, Alembic |
| Фронтенд (`frontend/`) | Vue 3, Pinia, Vite, Quill 2, Monaco Editor |
| Файлы | S3-совместимое хранилище (SeaweedFS), загрузка по presigned URL |
| Проверка кода | Judge0 1.13 (песочница isolate), воркер с очередью в Postgres |
| Прод | Docker Compose, Caddy (HTTPS от Let's Encrypt) |

Правила разработки для людей и ИИ-агентов — в [AGENTS.md](AGENTS.md).

## Типы заданий

Шаг курса создаётся запросом `POST /api/admin/modules/{id}/steps` с полем
`payload`: `type`, `max_score` (0–1000, по умолчанию 1), `content` (что видит
ученик), `answer_key` (правильный ответ, ученику не отдаётся) и `settings`.
Точные схемы всех типов — в `/docs` (`*Payload`).

| Тип (`type`) | Что это | Ответ ученика | Проверка (`settings.grading`) |
|---|---|---|---|
| `theory` | Теория (rich text) | пустой `{}` — отметка «прочитано» | `none`; балл всегда 0 |
| `single_choice` | Один верный вариант | `{"option_id": "<uuid>"}` | `auto` |
| `multiple_choice` | Несколько верных вариантов | `{"option_ids": ["<uuid>", ...]}` | `auto` |
| `free_text` | Свободный ответ: текст и/или файлы | `{"text": "...", "files": [id, ...]}` | `manual` — куратор |
| `programming` | Программа на Python 3 | `{"code": "..."}` | `tests`, `tests_and_review` или `manual` |

**Общие настройки всех заданий** (`settings`):

- `max_attempts` — число попыток (по умолчанию без ограничений). Новое
  решение можно отправить, пока предыдущее не на проверке, остались попытки и
  не набран максимальный балл; в зачёт идёт лучший балл.
- `show_answer` — когда ученик может посмотреть правильный ответ:
  `never` (по умолчанию), `after_wrong`, `after_attempts_exhausted`,
  `after_solved`.

**`theory`** — `content.body`: текст в формате TipTap/ProseMirror JSON.

**`single_choice` / `multiple_choice`**

- `content`: `question` (rich text), `options` — от 2 до 50 вариантов
  `{"id": "<uuid>", "text": "..."}`. Постоянные `id` позволяют менять порядок
  вариантов, не ломая правильный ответ.
- `answer_key`: `{"correct": "<uuid>"}` / `{"correct": ["<uuid>", ...]}`.
- `multiple_choice`, `settings.scoring`: `all_or_nothing` (по умолчанию) или
  `partial` — балл пропорционален `(верно выбранные − ошибочно выбранные) /
  число верных`, не меньше 0; выбрать всё подряд не выгодно.
- Почему такой балл: в решении всегда есть счётчики `result_details`
  (`correct_picked`, `wrong_picked`, `correct_total`) — они не выдают, какой
  вариант верный. Разбор по каждому варианту (`explanation`: выбран ли,
  верен ли) ученик видит, только когда `show_answer` уже открыл ответ.

**`free_text`**

- `content`: `question`, `max_files` (0–10, по умолчанию 0 — без файлов),
  `min_files` (сколько файлов обязательно), `require_text` (текст обязателен),
  `allowed_mime` (например `["image/jpeg", "image/png"]`, пусто — любые).
  «Обязательно текст и фото»: `require_text: true`, `min_files: 1`.
- `answer_key` — для куратора: `reference` (эталонный ответ), `criteria`
  (критерии), `files` (эталонные файлы с `purpose: answer_key`). Ученику,
  когда `show_answer` разрешает, показывается только `reference`.
- Файлы ученик загружает через `POST /api/files` с `purpose: submission`,
  до 20 МБ каждый.

**`programming`**

- `content`: `statement` (условие), `languages` — допустимые языки (один или
  несколько из `python3`, `javascript`, `cpp`, `csharp`, `go`, `pascal`;
  по умолчанию `["python3"]`; порядок сохраняется, первый — по умолчанию),
  `time_limit_ms`
  (100–15000, по умолчанию 2000), `memory_limit_mb` (16–512, по умолчанию
  256), `template` (заготовка кода), `samples` — открытые примеры
  `{"input", "output"}`, их вывод ученик видит полностью.
- `answer_key`: `test_groups` — группы скрытых тестов `{"name", "points",
  "tests"}`; тест — текстом (`input`, `output`) или файлами (`input_file`,
  `output_file`, загруженные с `purpose: answer_key`: вход до 16 МБ, вывод до
  4 МБ, все файлы задания до 128 МБ); `reference_solution` — эталонное решение.
- `settings.grading`: `tests` (только тесты), `tests_and_review` (тесты, затем
  куратор выставляет итоговый балл), `manual` (только куратор, тесты не
  обязательны).
- `settings.scoring`: `all_or_nothing` (по умолчанию — полный балл, только если
  прошли все тесты) или `per_group` (сумма баллов полностью пройденных групп;
  сумма `points` групп должна равняться `max_score`).
- По скрытым тестам ученик видит только вердикты (`ok`, `wrong_answer`,
  `time_limit`, `runtime_error`, `compilation_error`); правильный ответ после
  `show_answer` — только эталонное решение, тесты никогда.

- Решение: `{"code", "language"}`. `language` должен быть из `languages`
  шага; его можно не указывать, только если язык у шага один.
- Языки описаны в `backend/src/languages.py`: в шаге хранятся наши ключи, а не
  номера Judge0. В момент проверки ключ сопоставляется с языком из
  `GET /languages` самого Judge0 (берётся новейшая версия, например «Python
  (3.8.1)» → `python3`), список кэшируется на `JUDGE0_LANGUAGES_TTL_SECONDS`.
  Поэтому обновление Judge0 не ломает шаги и не требует миграции данных. Если
  Judge0 языка не предлагает, решение получает статус `error` с понятным
  сообщением (без повторов), остальное работает. `GET
  /api/programming/languages` — список языков с пометкой `available`
  (предлагает ли их Judge0 сейчас) для формы автора.
- Ограничение: `template` и `reference_solution` пока одни на все языки.

Новый тип добавляется одним модулем в `backend/src/steps/types/`.

## Оболочка кабинета

После входа навигация и заголовок страницы остаются на месте. Прокручивается
только материал внутри области содержимого. Навигацию можно свернуть до иконок.
Административный заголовок занимает отдельную полосу на всю ширину содержимого.

## Кабинет администратора

Фронтенд открывает администратору страницы курсов, конструктора, публикации,
истории редакций, групп и пользователей. Создание курса начинается в разделе
«Курсы». В конструкторе можно изменить настройки, добавить и упорядочить
модули и шаги, скрыть шаг. Редактор поддерживает пять типов шагов из API;
сохранение существующего шага создаёт новую редакцию и передаёт номер исходной
редакции для защиты от одновременной правки. Существенное изменение ответа
нужно отметить перед сохранением, чтобы старые решения считались устаревшими.
В конструкторе выбранный шаг можно править справа от списка модулей. Список
модулей и шагов прокручивается внутри боковой панели; форма добавления модуля
остаётся видимой в её нижней части. Редактор шага прокручивается отдельно.
Шаги перетаскиваются за захват «⋮⋮» только в пределах своего
модуля, модули — в пределах курса. Строка добавления шага находится под списком
шагов модуля. Название шага хранится как помеченный заголовок его документа,
поскольку отдельного поля названия в API нет.
Реализация разделов и их API-клиенты находятся в `frontend/src/modules/admin/`
по папкам `courses/`, `steps/`, `groups/` и `users/`; общие типы и стили — в
`shared/`. Папки `frontend/src/pages/admin/<страница>/` содержат компоненты-входы,
константы путей и массивы маршрутов; `frontend/src/pages/admin/routes.ts`
объединяет их для основного роутера.

Текст задания редактируется в Quill и сохраняется как TipTap/ProseMirror JSON,
который принимает API. Кнопка изображения загружает файл через `POST /api/files`
с `purpose: content` и presigned URL. В документе хранится ID файла; ссылка
для просмотра запрашивается заново при открытии редактора. Изображения по
сторонней ссылке в содержание не сохраняются. Поле Quill растёт по содержимому,
а его панель инструментов переносится внутри доступной ширины.
Курс публикуется через настройку
`is_published`; версий курса в текущем API нет. Экран импорта позволяет
предварительно разобрать текст `.txt`, но создание шагов из методички и разбор
`.docx` ожидают серверного контракта.
Эталонные файлы свободного ответа и большие скрытые тесты программирования
загружаются с `purpose: answer_key` и доступны в редакторе шага.
## Прогресс

Прогресс ученика по курсу — два числа и разбивка по шагам
(`GET /api/courses/{id}/progress`; итог есть и в списке курсов, и в оглавлении):

- **Засчитано шагов** — «7 из 12», в процентах (`steps_completed`,
  `percent`). Шаг засчитан, когда улучшить его уже нельзя или его принял
  куратор: набран максимум (теория — просмотрена), **или** есть баллы и не
  осталось попыток (9 из 10 — засчитан), **или** куратор принял решение с
  любым баллом. Без баллов и без попыток — не засчитан. Из засчитанных
  `steps_passed` — сколько на максимум.
- **Набрано баллов** — «23 из 40»: сумма лучших баллов по шагам, частичные
  баллы учитываются.
- **По каждому модулю** — те же числа (`modules` в ответе, `progress` у
  модуля в оглавлении); итог курса — сумма по модулям.
- **По каждому шагу**: состояние (`not_started`, `checking` — на проверке,
  `failed` — пока без баллов, можно ещё, `attempts_exhausted`, `partial`,
  `passed`), сколько баллов из скольких, кто оценил (`auto` или `curator`),
  какая попытка засчитана.
- **Следующий шаг** (`next_step_id`) — «сначала вперёд»: первый открытый
  шаг, который ещё не начат или пока без баллов (и попытки есть); если таких
  нет — шаг с частичным баллом, где остались попытки, чтобы улучшить. Шаги
  без попыток и на проверке пропускаются; если делать нечего — `null`.

Правила подсчёта:

- В зачёт идёт **лучшая** попытка. Оценка куратора засчитывается так же, как
  автоматическая: балл куратора — такой же балл.
- Считаются только видимые шаги курса.

| Изменение курса | Что с прогрессом |
|---|---|
| Добавлен шаг | Появляется как «не начат», итог растёт: 7 из 12 → 7 из 13 |
| Изменён порядок шагов | Ничего, кроме порядка |
| Шаг скрыт или удалён | Выпадает из подсчёта; решения остаются в истории |
| Задание поправлено | Ничего не меняется |
| Задание поправлено как **существенное изменение** (`is_breaking`) | Прежний результат сохраняется (`from_previous_version: true`), ученик получает новые попытки. Если изменился максимум, прежний балл сохраняет свою долю: 2 из 2 → 4 из 4 |

Куратор видит итог каждого ученика своей группы:
`GET /api/groups/{id}/courses/{id}/progress`. Прогресс считается из решений
при запросе, одним запросом на любое число учеников, поэтому при изменениях
курса и оценок ничего не пересчитывается заранее.

## Рейтинг

**Формула: рейтинг ученика = сумма набранных баллов по курсу** — ровно
`points_earned` прогресса: лучшая попытка по каждому шагу, частичные баллы
учитываются, балл куратора засчитывается наравне с автоматическим.

Почему так: правило объясняется ребёнку одной фразой — «за каждое задание —
твои баллы», а любой балл можно проследить до конкретной попытки в разбивке
прогресса. Прогресс показывает, сколько курса пройдено; рейтинг — место среди
своей группы.

- **Место** = 1 + число одногруппников, у которых баллов строго больше.
  Равные баллы делят место: 6, 4, 4, 0 → места 1, 2, 2, 4.
- Рейтинг строится внутри текущей группы ученика по курсу, среди записанных
  на курс; без группы рейтинга нет.

**Ученик видит только своё** (`GET /api/courses/{id}/rating`): баллы, место,
сколько человек делят его, размер группы — и обезличенные цели:

- **следующее место** — ближайший результат строго выше (равные пропускаются):
  его место, баллы и разрыв `gap`;
- **первое место** — баллы лидера и разрыв (если ученик сам первый — разрыва
  нет).

Чтобы обойти, нужно набрать **больше** `gap`: ровно столько даёт только
ничью. Где взять баллы — `opportunities`: шаги, где ещё можно заработать
(«модуль «Циклы», шаг 3»), сначала непройденные — `complete`, затем с
частичным баллом — `improve`; для каждого — сколько баллов он может
добавить. Для каждой цели есть `plan` — первые по этому порядку шаги, которых
хватает, чтобы обойти; если не хватает даже всех — `reachable: false`.
Шаги без попыток, на проверке и теория (без баллов) в советы не входят.

**Куратор** видит рейтинг своей группы с именами:
`GET /api/groups/{id}/courses/{id}/rating`. Рейтинг считается на лету из
тех же данных, что и прогресс, — одним запросом на группу.

## Отставание

Отставание от графика — статус ученика по конкретному курсу, по дедлайнам его
группы. Дедлайн — только информация: он **не блокирует** сдачу, решения после
срока принимаются и проверяются как обычно (с отметкой `is_late`).

**Задание просрочено**, если его дедлайн (свой или унаследованный) прошёл, а
шаг **не засчитан** (см. «Прогресс»):

- решение, отправленное позже и засчитанное, снимает просрочку — отставание
  показывает текущее положение;
- решение на проверке — не просрочка: ученик свою часть сделал;
- попытки исчерпаны без баллов — просрочка остаётся: исправить уже нельзя, и
  куратор должен это видеть.

| Статус | Когда |
|---|---|
| `on_track` — в графике | просроченных заданий нет |
| `slowed` — замедлился | есть просроченные, но ни одно — больше чем на 7 дней |
| `falling_behind` — выпадает | хотя бы одно просрочено больше чем на 7 дней |

**Причина** — список просроченных шагов (самые давние первыми): где шаг
(модуль и номер), срок, на сколько дней просрочен и его состояние:
`not_started` — не начат, `failed` — пока без баллов, `partial` — частично,
`attempts_exhausted` — попытки кончились без баллов.

Где видно:

- ученик — блок `lag` в своём прогрессе (`GET /api/courses/{id}/progress`);
- куратор — статус и причины у каждого ученика в сводке группы
  (`GET /api/groups/{id}/courses/{id}/progress`) и список только отстающих,
  сначала «выпадает», затем «замедлился»
  (`GET /api/groups/{id}/courses/{id}/lagging`).

У ученика без группы дедлайнов нет — он всегда «в графике».

## Локальная разработка

```bash
cd backend
cp .env.example .env        # заполнить секреты; JUDGE0_AUTH_TOKEN — с сервера
docker compose up -d --build
```

- API: http://localhost:8000 (документация: http://localhost:8000/docs)
- Фронтенд: http://localhost:5173
- Первый администратор:
  `docker compose exec dev uv run --no-sync python src/set_role.py <username> admin`

Код заданий по программированию проверяется на серверном Judge0
(`JUDGE0_URL` в `.env`): локально Judge0 не работает на Docker Desktop,
которому нужен cgroup v1.

### Тесты и линтер

```bash
cd backend
uv sync
uv run pre-commit install                 # один раз: ruff перед каждым коммитом
TEST_DB_URL="postgresql+asyncpg://user:pass@localhost:5432/app_test" uv run pytest
```

Без `TEST_DB_URL` запускаются только юнит-тесты. База из `TEST_DB_URL`
очищается при каждом запуске — не указывайте рабочую.

Автопроверку целиком — на работающем стенде с настоящим Judge0 — проверяет
набор решений с ожидаемыми вердиктами: `samples/verdicts/README.md`.

## Переменные окружения

Все настройки — в `backend/.env` (шаблон с комментариями —
`backend/.env.example`, в git не попадает). Файл читают:

- **docker compose** — подставляет значения в `docker-compose.yml` и
  `docker-compose.prod.yml`. Секреты помечены `${VAR:?}`: без них стек не
  запустится;
- **приложение** (pydantic-settings, `backend/src/config.py`) — при запуске
  из `backend/` и в локальном стеке (`env_file: .env`).

Секреты генерируются так:
`python3 -c "import secrets; print(secrets.token_urlsafe(32))"`.

**Обязательные** — и локально, и на сервере:

| Переменная | Назначение |
|---|---|
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Учётная запись и база Postgres. Пароль применяется только при создании тома `pgdata`: чтобы сменить его позже — `ALTER USER` или пересоздать том |
| `JWT_KEY` | Ключ подписи токенов входа; смена разлогинивает всех |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Ключи файлового хранилища (SeaweedFS) |
| `S3_BUCKET` | Бакет для файлов, по умолчанию в шаблоне `zebra` |
| `JUDGE0_AUTH_TOKEN` | Токен доступа к Judge0 (`X-Auth-Token`); локально — тот же, что на сервере |

**Только сервер** (`docker-compose.prod.yml`):

| Переменная | Назначение |
|---|---|
| `SITE_DOMAIN`, `S3_DOMAIN`, `JUDGE0_DOMAIN` | Домены сайта, файлового хранилища и Judge0; для каждого нужна A-запись |
| `ACME_EMAIL` | E-mail для Let's Encrypt (не `example.com` — такой отклоняется) |
| `JUDGE0_ADMIN_TOKEN` | Токен служебных эндпоинтов Judge0 |
| `JUDGE0_DB_PASSWORD`, `JUDGE0_REDIS_PASSWORD` | Пароли внутренних Postgres и Redis Judge0 |
| `JUDGE0_WORKERS` | Сколько решений Judge0 выполняет параллельно; по умолчанию `2` |

**Только локально** (на сервере их задаёт `docker-compose.prod.yml`):

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `JUDGE0_URL` | Адрес Judge0 для локального воркера | серверный Judge0 |
| `CORS_ORIGINS` | С каких адресов фронтенд может обращаться к API (JSON-список) | `localhost:5173`, `:3000` |
| `S3_PUBLIC_ENDPOINT` | Адрес хранилища, который видит браузер (в presigned URL) | `http://localhost:9000` |
| `POSTGRES_PORT`, `API_PORT`, `S3_PORT`, `FRONTEND_PORT` | Порты на хосте | `5432`, `8000`, `9000`, `5173` |
| `VITE_API_URL` | Адрес API, вшиваемый в сборку фронтенда | `http://localhost:8000/api` |

**Необязательные**, с разумными значениями по умолчанию из `config.py`:

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `JWT_ALGORITHM` | Алгоритм подписи токенов | `HS256` |
| `ACCESS_TOKEN_EXPIRE_MINUTES`, `REFRESH_TOKEN_EXPIRE_MINUTES` | Время жизни токенов | `10`, `10080` (неделя) |
| `MAX_UPLOAD_MB` | Предельный размер одного загружаемого файла | `20` |
| `PRESIGNED_URL_TTL_SECONDS` | Срок действия ссылок на загрузку и скачивание | `900` |
| `S3_REGION` | Регион S3 (для SeaweedFS не важен) | `us-east-1` |
| `JUDGE0_LANGUAGES_TTL_SECONDS` | Как долго кэшируется список языков Judge0 | `300` |
| `WORKER_CONCURRENCY` | Сколько решений воркер проверяет одновременно | `2` |
| `JUDGE_MAX_RETRIES` | Повторы проверки при сбоях Judge0 или хранилища | `3` |
| `JUDGE_STALE_AFTER_SECONDS` | Через сколько «зависшая» проверка возвращается в очередь | `600` |
| `JUDGE_MAX_OUTPUT_KB` | Предельный вывод программы (не больше лимита Judge0) | `4096` |
| `JUDGE_BATCH_MAX_MB` | Предельный объём тестов в одном запросе к Judge0 | `16` |
| `TEST_INPUT_MAX_MB`, `TEST_FILES_TOTAL_MB` | Предельный вход одного теста и всех файлов тестов задания | `16`, `128` |
| `WORKER_FILE_CACHE_MB` | Кэш файлов тестов в памяти воркера | `64` |

На сервере приложению передаются только переменные, перечисленные в
`x-app-env` файла `docker-compose.prod.yml` (секреты и токены из таблиц
выше). Чтобы изменить на сервере необязательную настройку, её нужно
добавить туда же — просто строка в `.env` на прод не повлияет.

**Задаются docker compose сами**, в `.env` их не пишут: `DB_URL` и
`DB_PASSWORD` (собираются из `POSTGRES_*`; пароль передаётся отдельно, чтобы
в нём работали любые символы), `S3_ENDPOINT`, на сервере — `JUDGE0_URL`,
`CORS_ORIGINS`, `S3_PUBLIC_ENDPOINT` (по доменам), `FORWARDED_ALLOW_IPS`.

**Тесты**: `TEST_DB_URL` — отдельная база, очищается при каждом запуске
(см. «Тесты и линтер»).
