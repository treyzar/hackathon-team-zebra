# Правила для агентов и участников

Эти правила обязательны для любых изменений в репозитории — от людей и от
ИИ-агентов (Claude Code, Codex, Cursor и др.). Они следуют из критериев
оценки проекта: структура, качество кода, документация, проверяемость.
Если правило мешает задаче — не обходите его молча, а скажите об этом.

## 1. Структура и модульность

Бэкенд — `backend/src/`, точка входа API — `server.py`, воркер проверки кода —
`worker.py`. Каждая предметная область — свой пакет:

| Что | Где |
|---|---|
| Кабинет администратора (авторинг курсов, группы, роли) | `courses/admin_api.py`, `groups/api.py`, `admin.py` |
| Кабинет ученика (курсы, шаги, решения) | `courses/student_api.py` |
| Кабинет куратора (очередь проверки, дедлайны) | `submissions/review_api.py`, `groups/deadlines.py` |
| Модель курса: курс → модули → шаги → редакции | `courses/models.py`, `courses/service.py` |
| Доступ к шагам (последовательное открытие) | `courses/access.py` |
| Типы шагов | `steps/types/<тип>.py`, контракт — `steps/base.py`, реестр — `steps/registry.py` |
| Проверка решений: отправка, попытки, вердикты | `submissions/service.py`; тесты кода — `judge.py` + `worker.py` |
| Прогресс по курсу, попытки по текущей версии шага | `progress/service.py`, `progress/stats.py`, API — `progress/api.py` |
| Файлы (S3, presigned URL) | `files/` |
| Документация доступа к эндпоинтам | `access_docs.py` |

Правила:

- **Новый тип шага** — один модуль в `steps/types/` плюс импорт в
  `steps/__init__.py`. Если для этого приходится менять код вне `steps/` —
  значит, не хватает метода в контракте `StepType`: расширьте контракт, а не
  добавляйте `if step.type == ...` в общий код.
- **Роли не смешиваются в одном роутере.** Эндпоинты для разных ролей — в
  разных роутерах (кабинетах); общая логика — в `service.py` своего пакета.
- **Прогресс, рейтинг и отставание** — в модуле `progress/`, а не внутри
  эндпоинтов; эндпоинты только вызывают его. Порядок шагов курса — только
  через `courses.service.visible_steps_in_order`.
- **Вычисляемое не хранится.** Унаследованные дедлайны, отметка «после
  дедлайна», блокировка шагов считаются при показе; в базе — только то, что
  внёс человек. Храните производное значение, только если без этого не
  обойтись, и объясните почему в комментарии.
- Код живёт в Docker: локально `backend/docker-compose.yml`, прод —
  `backend/docker-compose.prod.yml`. Новый сервис добавляется в оба.

## 2. Качество кода и комментарии

- Пишите как окружающий код: те же имена, идиомы, плотность комментариев.
  Python 3.12, async SQLAlchemy, Pydantic v2; ruff (`E F I B UP`).
- Не дублируйте логику: одно правило — одна функция, которой пользуются все
  места (пример: `submit_block_reason` и для отправки, и для `can_submit`).
- Комментарии — на английском, объясняют **почему**, а не пересказывают код.
  Обязательно поясняйте сложные участки: проверку решений и подсчёт баллов,
  расчёт рейтинга, правило отставания, изменение опубликованного курса
  (редакции, `is_breaking`, устаревшие решения), права доступа.
- Бессодержательные комментарии (`# get user`, `# loop`) — не писать.
- Секреты не печатать и не логировать; настройки — только через `config.py`
  и `.env` (шаблон `backend/.env.example`), в `docker-compose` без значений
  по умолчанию для секретов.

## 3. Инварианты предметной области

Нарушение любого из них — ошибка, даже если тесты зелёные.

- `answer_key` (правильные ответы, скрытые тесты) никогда не уходит ученику.
  Показ ответа — только через `StepType.reveal`/`explain` и только когда
  разрешает `show_answer`. Скрытые тесты не раскрываются никогда.
- Редакции шага неизменяемы: правка задания = новая редакция. Решение всегда
  ссылается на редакцию, на которую отвечал ученик.
- Курсы, модули и шаги удаляются мягко (`deleted_at`).
- Файлы: `content` — всем вошедшим, `answer_key` — кураторам и админам,
  `submission` — владельцу, куратору его группы и админам.
- Куратор видит только учеников своих групп. Чужие решения и файлы — 404,
  а не 403: сам факт их существования не раскрывается.
- Каждое изменение схемы БД — миграция Alembic; `alembic check` чистый.

## 4. Документация

- **Язык документации — русский** (README, `backend/deploy/README.md`,
  описания в `/docs`). Код и комментарии — на английском.
- `README.md` должен содержать: стек, структуру, зависимости, команды запуска,
  переменные окружения, наполнение демоданными, тестовые учётные записи трёх
  ролей, модель курса, типы заданий, формулу рейтинга, правило отставания,
  как добавить новый тип шага, ограничения. Изменили поведение — обновите
  соответствующий раздел и «Статус» в том же коммите.
- Доступ к эндпоинту описывается автоматически по зависимостям
  (`require_admin`, `require_curator`, токен). Проверки внутри эндпоинта
  («только свои решения») описывайте декоратором `@access_note(...)`.
  Тест `test_openapi.py` падает, если у эндпоинта нет строки доступа.
- Для эндпоинтов со сложным телом запроса давайте пример в схеме Pydantic
  (`examples`), чтобы `/docs` был пригоден для ручной проверки.
- Демоданные — из `samples/`; загрузка демоданных и тестовые пользователи
  трёх ролей должны подниматься одной документированной командой.

## 5. Проверяемость

Ключевая логика проверяется автотестами независимо от UI:

- вердикты проверки по тестам (`test_judge.py`, `test_worker.py`,
  `test_step_types.py`), статусы ручной проверки, правила попыток;
- доступ (роли, группы, последовательное открытие шагов), дедлайны;
- расчёт прогресса и рейтинга, правило отставания — когда появятся.

Правила:

- Новая логика — вместе с тестами в том же изменении. Тесты проверяют
  поведение через API или контракт типа, а не внутренние детали.
- Тест должен ловить поломку: для важного правила убедитесь, что при его
  отключении тест падает (временно сломайте код — тест красный — верните).
- Для программирования поддерживайте набор решений с ожидаемыми вердиктами
  (верное, неверное, превышение времени, ошибка выполнения).
- Внешние сервисы в тестах подменяются: Judge0 — фейком API или локальным
  запуском (`LocalJudge`), S3 — `FakeStorage` из `conftest.py`.

## 6. Команды

```bash
cd backend
cp .env.example .env              # заполнить секреты
docker compose up -d --build      # локальный стек: API :8000, фронтенд :5173

uv sync && uv run pre-commit install          # один раз
uv run ruff check . && uv run ruff format .   # линтер и форматирование

# Тесты API нужна отдельная БД — она очищается при каждом запуске!
TEST_DB_URL="postgresql+asyncpg://user:pass@localhost:5432/app_test" uv run pytest

# Миграция после изменения моделей (DB_URL — на базу с применёнными миграциями)
uv run alembic revision --autogenerate -m "что изменилось"
uv run alembic upgrade head && uv run alembic check
```

Фронтенд (`frontend/`): `npm run lint`, `npm run type-check`, `npm run build`.

Перед тем как сказать «готово»: ruff чистый, все тесты зелёные (с
`TEST_DB_URL`), миграция применяется и откатывается. Если что-то не удалось
проверить — прямо скажите, что именно.

## 7. Git

- Коммит — одно логическое изменение вместе с тестами, миграцией и
  документацией. Не коммитьте `.env`, `.idea/`, артефакты покрытия.
- Сообщение — по-русски, в стиле истории проекта:
  `feat: добавит …`, `fix: исправит …`, `docs: …`; ниже — список изменений.
- Pre-commit-хук (ruff) не отключать; если он падает — исправить причину.
- Не переписывать опубликованную историю (`push --force`, `rebase` запушенного).
